# Silhouettes

Mountain silhouette assets are **terrain-derived**: each peak's ridge line is
projected from USGS 3DEP 1/3 arc-second DEM data using the deterministic
engine in `src/data/silhouette.ts`. No silhouette in this repository is
hand-drawn, mock-sourced, or generated at runtime in the browser.

The frozen rules in [`data-contract.md`](./data-contract.md) apply to this
milestone: no fabricated ridge lines from the design mock, no external tile
services at build or runtime, no provider-specific behavior. Silhouettes are
plain static SVG files under `public/silhouettes/`.

## 1. Separation of concerns (frozen)

- **Terrain-derived geometry** — the closed SVG path (`d` attribute).
  Produced by projecting the DEM crop for each of four cardinal directions
  (N, E, S, W). A pure function of the committed DEM bytes, grid dimensions,
  and renderer config. No randomness, no wall clock, no network.
- **Deterministic artistic styling** — fill, stroke, fill-opacity, and viewbox
  chosen from a fixed, versioned palette keyed by peak id via FNV-1a. Styling
  never feeds back into geometry; geometry never carries a timestamp.
- **Host-neutral.** Whatever is shipped must be plain static assets (SVG/other)
  under `public/` or `src/assets/` — no runtime geometry generation, no
  external tile services, no provider-specific behavior.

## 2. Data layout

```
data/silhouettes/
  manifest.json                  # compact source manifest (committed)
  <spk-id>/
    <spk-id>.bin                 # committed compact DEM crop (LE float32, row-major)
    <spk-id>.json                # provenance metadata (committed)
public/silhouettes/
  <spk-id>/
    N.svg  E.svg  S.svg  W.svg   # generated closed SVG silhouettes (committed)
```

The compact `.bin` crops are committed to the repository so the build and
`--check` gate are fully offline. They are derived from USGS 3DEP 1/3
arc-second DEM tiles; the raw tile cache lives in `data/terrain/` and is
git-ignored (large binary, not committed).

## 3. Provenance

Each `<spk-id>.json` records:

- `width`, `height` — crop dimensions in cells
- `nodata` — no-data sentinel (default `-9999`)
- `sample_sha256` — SHA-256 of the committed `.bin`
- `source` — DEM source label (e.g. "USGS 3DEP 1/3 arc-second")
- `source_sha256` — SHA-256 of the original DEM tile bytes, if available
- `retrieved_at` — UTC ISO 8601 retrieval timestamp
- `retrieval_method` — how the tile was obtained (manual / 3DEP download)
- `observer_lat`, `observer_lon`, `observer_elevation` — peak center
  (from the SPS dataset where available; v1 data gap where not)

`data/silhouettes/manifest.json` is regenerated by the CLI on every
`pnpm generate:silhouettes` run and committed alongside the SVGs. It records
the renderer version, per-peak sample checksums, SVG checksums, and
elevation ranges. `elevations.min_m` / `max_m` are the actual minimum and
maximum values (in metres) across the entire committed `.bin` sample grid —
the audit record of the terrain's elevation range, distinct from the
per-view normalization range used for geometry.

## 4. Engine (`src/data/silhouette.ts`)

- `readTerrain(bytes, meta)` — decode little-endian float32 row-major DEM
  crop; rejects empty/short buffers and bad dimensions.
- `projectView(grid, direction)` — for each cardinal direction, walk the
  sight line from the observer outward and keep the **nearer-weighted maximum**
  elevation per horizontal bin. Each step of distance multiplies a cell's
  apparent elevation by `SIGHT_DECAY` (0.8), so a nearer ridge can occlude a
  farther one even when the farther cell is taller. The walk is order-dependent
  (observer-near first), which makes N/S and E/W skylines genuinely distinct
  views of the same terrain.
- `normalizeToY` — rescale elevations into SVG y units, pinned to the
  sample's own min/max so the geometry is a deterministic function of the
  terrain alone.
- `smoothBox` — deterministic uniform box smoothing (integer kernel width,
  clamped endpoints). No randomness, no iteration until convergence.
- `buildPath(points, baselineY)` — emit a closed, valid SVG path
  (starts with `M`, ends with `Z`) with coordinates rounded to 2 decimal
  places for byte-stable output.
- `renderSilhouettes(grid, config)` — render all requested directions;
  returns closed paths + points + min/max elevations.
- `renderSvg(result, direction)` — wrap the closed path in a fixed
  1200×400 viewbox with deterministic styling.
- `artisticStyle(peakId)` — deterministic fill/stroke from FNV-1a hash.

The engine is a pure function of `(terrain sample, config, parameters)`.
It never touches the filesystem, the network, or the wall clock.

## 5. CLI (`scripts/silhouette/generate-silhouettes.mjs`)

| Command | Description |
|---|---|
| `pnpm generate:silhouettes` | Generate SVGs + manifest from committed DEM crops |
| `pnpm generate:silhouettes:dry-run` | Print what would change; write nothing |
| `pnpm check:silhouettes` | CI drift gate: committed outputs must reproduce byte-for-byte |

The generator reads `data/silhouettes/<id>/<id>.bin` + `<id>.json`, renders
all four cardinal directions, writes `public/silhouettes/<id>/<D>.svg`, and
replaces `data/silhouettes/manifest.json`. In `--check` mode it fails if
any committed file does not reproduce.

## 6. Validator (`scripts/silhouette/validate-silhouettes.mjs`)

`pnpm validate:silhouettes` scans `public/silhouettes/` and fails on:

- **missing** — a peak directory exists but a direction SVG is absent
- **blank** — no `<svg>` or `<path>` element, or a path with no drawing commands
- **malformed** — not well-formed XML, not exactly one root `<svg>`, path `d`
  attribute not a valid closed path (must start with `M`, end with `Z`)
- **out-of-viewbox** — path coordinates outside the declared viewBox
- **duplicate** — two SVG files with identical bytes (an error within a peak,
  or a hash collision between two different peaks)

The validator is a technical gate only; it does not check source provenance
(that is the job of the manifest + data-refresh contract).

## 7. Peak coordinate gap (v1)

The SPS 29th Edition exposes UTM coordinates for only a small subset of
peaks (19 of 248 rows carry a non-empty `utm_raw`).  The full Peakbagger
lid=5051 snapshot does not expose coordinates in its table, so the
canonical dataset carries no per-peak lat/lon.

Pilot 08 bridges this gap for its 8 pilot peaks by geocoding each peak
through OpenStreetMap Nominatim (ODbL attribution) and recording the
resolved coordinates in the per-peak sidecar JSON
(`data/silhouettes/<spk-id>/<spk-id>.json`).  These coordinates are
authoritative for the pilot only; a full 247-peak coordinate source
(e.g. Peakbagger's own peak data, or a curated lat/lon table) is a
future milestone.

The silhouette generator (`generate-silhouettes.mjs`) does **not** depend
on coordinates — it consumes the committed `.bin` crops directly.
Coordinates are used only at acquisition time to position the crop
window over the peak.

## 8. CI

The silhouette `--check` gate is wired into the CI pipeline alongside the
existing SPS / Peakbagger / reconcile drift gates. CI never fetches DEM
tiles; it only reproduces committed SVGs from committed compact crops.
